# ADR 0002 — Use TEXT UUID primary keys for application tables

Date: 2025-10-28

Status: Accepted

## Context

The project uses SQLite for local and containerized development and stores application data in a single DB file. Different parts of the codebase and SQL fixtures were inconsistent about primary key types for domain tables (users, applications, resumes, attachments, application_status_history, schema_migrations): some SQL fixtures used INTEGER AUTOINCREMENT, while application code and runtime seeding used UUID strings (generated by the app). This caused repeatable issues when running Playwright E2E in Docker: missing or mismatched records and auth failures when seeded host DB data did not map to container DB records.

## Decision

Standardize on UUIDs stored as TEXT for primary keys across the schema and application code. Concretely:

- Use `id TEXT PRIMARY KEY` for domain tables (users, applications, resumes, attachments, application_status_history, schema_migrations).
- Generate UUIDs in application code (Node.js `crypto.randomUUID()` or equivalent) when inserting rows and when seeding test data.
- Avoid database-specific UUID generation expressions (e.g., SQLite `randomblob()` defaults) to preserve portability and clarity.

## Rationale

- Consistency: The application and test helpers already expected UUID strings in many places. Standardizing avoids type mismatches.
- Portability: Generating UUIDs in application code avoids SQLite-specific SQL expressions that are not portable or are brittle when run in other engines.
- Test reliability: E2E tests seed verified users and rely on predictable UUID values; using TEXT UUIDs in the schema allows seeding to succeed in containerized DBs without extra migration steps.
- Simplicity: TEXT primary keys avoid surprises with AUTOINCREMENT and sqlite_sequence interactions and with integer-vs-string comparisons in code.

## Consequences

- Positive
  - E2E tests run reliably against Docker containers (seeded UUID users map correctly to container DB rows).
  - Fewer portability surprises when moving to other SQL engines or when creating DB dumps.

- Negative / Migration cost
  - Existing local DB files created with INTEGER AUTOINCREMENT PKs will not match the new schema. Developers will need to recreate local DBs or migrate data if they want to preserve records.
  - Any scripts or external tooling that assumed numeric IDs must be updated.

## Migration notes

- For development: delete or re-create local DB (packages/api/data/resume.db) after pulling these changes. Scripts and test harnesses (init-db, seed-users) now create the tables with `TEXT PRIMARY KEY` and insert UUIDs.
- If you need to upgrade an existing DB in-place: export data, convert integer IDs to UUIDs in application code or a migration script, and update FK references accordingly. Prefer a fresh DB for test/dev environments.

## Security

- No sensitive data is affected by the key type change. UUID generation is done in application code; ensure secrets (e.g., TEST_ROUTE_SECRET, API keys) remain outside the repository. `.env.docker` has been sanitized to remove committed API keys.
